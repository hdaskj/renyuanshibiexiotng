# 数据库与核心代码实现说明

## 1. 本阶段目标

本阶段把 MVP 的数据库从“业务状态可用”升级为“可追溯、可约束、可清理”的实现，并让核心代码真正依赖规范化数据表，而不是只把检索结果保存在一段 JSON 中。

## 2. 数据库实现

### 2.1 表与职责

- `users`、`albums`、`album_members`：身份、相册所有权和参与成员关系。
- `search_requests`：参与者申请、所有者决策、有效期。
- `consents`：真正控制检索权限的授权快照。
- `search_sessions`：一次检索的模型版本、授权版本、查询和样本哈希。
- `search_results`：逐条保存 Top-K 排名、总分、三模态分项、解释和免责声明。
- `feedback_events`：引用真实结果 ID，保存相关/不相关/撤销及 30 天保留期限。
- `audit_events`：授权、审批、检索、反馈和撤回审计。
- `deletion_jobs`：撤回后派生数据的可查询清理任务。
- `outbox_events`：为后续可靠异步清理预留事务性事件。

### 2.2 关键约束

- 相册所有者、成员、申请人、决策人、授权主体均使用外键关联。
- 申请状态、授权状态、检索状态、反馈值、删除状态均有 CHECK 约束。
- 审计事件绑定 `album_id`，参与者与所有者只能读取授权相册范围内的审计。
- 同一会话的照片唯一，同一会话的排名唯一。
- 分项分值和总分限定在 0-100。
- 删除任务和 outbox 具有状态、尝试次数和到期时间索引。

### 2.3 PostgreSQL 迁移

- `V1__core_schema.sql`：核心业务表。
- `V2__seed_data.sql`：课程演示账户、相册和成员。
- `V3__core_relations_results_and_cleanup.sql`：外键、规范化结果、清理任务和 outbox。

H2 开发模式使用 `schema.sql` 重建同样的核心结构，确保本地演示不依赖 PostgreSQL。

## 3. 核心代码实现

### 3.1 检索结果规范化

`WorkflowService.startSearch` 现在会：

1. 校验申请人与授权。
2. 计算样本 SHA-256，但不保存原图。
3. 调用模型服务和向量索引。
4. 为每条结果生成独立 `resultId`。
5. 保存检索会话和逐条 `search_results`。
6. 同时保留结果 JSON 作为审计兼容快照。

`GET /search-sessions/{id}/results` 优先从 `search_results` 查询，再映射为 API DTO。

### 3.2 反馈

反馈接口必须同时提供 `sessionId` 和真实 `resultId`。服务端验证：

- 会话属于当前用户。
- 结果确实属于该会话。
- 反馈值为 `RELEVANT`、`IRRELEVANT` 或 `UNDO`。

反馈事件设置 30 天建议保留期限，并写入审计。

### 3.3 撤回与清理

撤回授权时：

1. consent 改为 `REVOKED`。
2. search request 改为 `REVOKED`。
3. 删除会话与规范化结果，立即阻断旧结果访问。
4. 创建 `deletion_jobs`，状态为 `PENDING`。
5. 创建 `outbox_events`，事件为 `CONSENT_REVOKED`。
6. 返回 `cleanupJobId`，可通过 `GET /deletion-jobs/{jobId}` 查询。

`CleanupWorker` 已实现数据库任务领取、尝试次数、完成/失败状态、审计和 outbox 发布。开发环境可启用 `CLEANUP_WORKER_SIMULATION=true` 验证全链路；生产环境必须关闭模拟并接入对象存储、缓存和 Milvus 的真实删除适配器。

## 4. 验证结果

- H2 全新建表成功。
- 申请、所有者批准、consent 创建、检索、逐条结果落库、反馈使用 resultId、撤回、清理任务查询和 Worker 完成状态通过。
- 自动冒烟测试返回 9 条结果，撤回状态 `CLEANUP_PENDING`，清理任务最终 `COMPLETED`。
- React E2E 已验证真实 API 检索、反馈和撤回。
